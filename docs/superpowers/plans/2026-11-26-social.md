# Social Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An adults-only social layer for players (an opt-in profile, follows, a feed of matches, rank-ups, photos and short posts, kudos and comments), with the moderation that Apple 1.2 and Google's UGC policy require, built as a hidden module.

**Architecture:** A global module `social` (`scope: "global"`, `availability: "hidden"`). A player can use it when the platform availability allows it, at least one of their clubs has it on, and they've opted in (18+, community rules accepted). Rules with no I/O (text screening, who sees what, report severity, deadlines) live in `@luvallplay/core/social`. Data and queries live in `apps/web/lib/social` and in a shared `apps/web/lib/moderation` (blocks, reports, actions) that the Marketplace reuses. The API is one endpoint file per module, as lane H's split requires. The app adds a Social section under Discover.

**Tech Stack:** Next.js 16 route handlers, Postgres (raw SQL through the `Db` type, as in `lib/juniors`), `@luvallplay/api` contract, React + TanStack Router/Query in `apps/app`, `@luvallplay/crypto` (encryption plan, Task 1), `node:test`, the journeys in `apps/web/tests/e2e/journeys.mjs`.

**Spec:** `docs/plans/luvallplay-build-plan.md` §8 item 3 (Social), §4.3 (store rules), §6.8 (juniors can't use social), §7.1 (`rally-coral` only around social moments); `./2026-11-26-social-marketplace-security-index.md`.

## Global Constraints

- Hidden until gate Z passes: `availability: "hidden"` in the manifest. Every endpoint answers `404 module_off` when the player has no access. Nothing in the app shows Social without access.
- **How "hidden" still passes review (Apple 2.3.1 forbids hidden or dormant features).** `hiddenModuleOn` (`lib/juniors/switch-rule.ts:36`) gains a `social` case: on only for clubs listed in the platform setting `SOCIAL_PILOT_TENANTS` (club ids; empty by default; read in production too, unlike `JUNIORS_AVAILABILITY`). The store review demo club is the first entry; pilot clubs are added when gate Z passes. The review notes say Social is live for pilot clubs. Nothing else switches it on.
- **Access is checked in one wrapper.** `appRoute` only checks `module` for club-scoped endpoints (`lib/app-api.ts:231`), so every `social.*` handler is built with `socialRoute(id, handler)`. It runs `socialAccess` **before** body parsing and before the limiter counts, and a contract test walks every `social.*` endpoint id and expects `404 module_off` with access off.
- **Suspensions outlive accounts.** They're kept in `player_suspensions (player_id, scope 'social'|'market'|'all', until, reason_code, email_index, phone_index)`. The indexes are blind indexes of the normalised email and phone, built with `CONTACT_INDEX_KEYS` (purposes `"suspension.email"`, `"suspension.phone"`). Deleting an account never deletes these rows, and joining checks them, so re-registering with the same email or phone stays suspended.
- **People are shown by social display name and a random public id** (`social_profiles.public_id`, 12 characters, base62), never by real name or `players.id`. Avatars are **initials only** in this plan: `players.avatar_url` hasn't been through the image check (`app-account.ts:35`). A checked avatar is a later task.
- **Cross-club reads go through two `SECURITY DEFINER` functions** that the migration creates and grants to the app role. Under `TENANT_SCOPE=enforce`, `club_members` and `tenant_modules` only show the deployment's club. `social_clubs_of(player_id) RETURNS SETOF bigint` gives the clubs where the person is a member and Social is on. `shares_social_club(a, b) RETURNS boolean`. No request code uses `unscopedPool()`. Every database test file in this plan also runs under `TENANT_SCOPE=enforce` with two clubs.
- Writes use `failClosed` shared rate limits and `withPlayerLock` for daily caps (encryption plan, Task 8).
- **Adults only.** Opting in needs a confirmation that the player is 18 or over, stored with a timestamp. `players` has no date of birth, so this is a self-declaration. The store age rating is set to match (17+ on Apple, Mature or 18+ on Play), and moderators can suspend someone pending re-verification. Junior profiles have no sign-in and can never have a social profile. Community rules can't be skipped.
- Limits: display name 1–40 characters, bio ≤160, post ≤500, comment ≤300. Text is trimmed and runs of whitespace collapsed.
- Report reasons: `spam`, `harassment`, `hate`, `sexual`, `violence`, `self_harm`, `child_safety`, `scam`, `prohibited_item`, `other`. `child_safety`, `sexual`, `self_harm`, `violence` and `hate` are **serious**: they go to the platform queue, are due within **12 hours**, and email the platform moderators at `PLATFORM_MODERATOR_EMAILS` through their own sender (never the club's `ALERT_ADMIN_EMAILS`). Serious targets are shown blurred until the moderator chooses to look. Reports about a club's own owners or admins also go to the platform queue. Everything else is due within **24 hours** (Apple 1.2; inside NZ HDCA's 48 hours).
- Report details (free text, ≤1,000) are sealed with `MODERATION_KEKS`, binding `["report", reportId]`. No key, no details stored. The report itself is still accepted.
- A block works both ways: neither person sees the other's profile, posts or comments, and neither can follow the other. Blocking removes any follow between them.
- A match post names the opponent only if the opponent also has a social profile. Otherwise it reads "won a match" with the score and no name.
- Photo posts only use photos the existing check (`lib/photo-moderation.ts`) approved. `needs_review` keeps the post `held`.
- Every moderation action writes one append-only `moderation_actions` row. The app's database role can't update or delete those rows.
- Everything visible in English and Vietnamese (`packages/i18n`, new namespace `social`). UI follows the index's "Why some apps look AI-built" rules.
- Migration additive and numbered at merge. Rehearsal note in `docs/rehearsals/`.

## Review Focus

1. **Someone blocked comments on an old post** that the blocker can still see through a mutual club. The comment must not appear for the blocker, and the blocked person's comment box on the blocker's posts must refuse (`404 not_found`). Task 4 test.
2. **A player who leaves their last social club** (or the club switches the module off) keeps their data but disappears from feeds and gets `module_off`. Task 3 test.
3. **The same Arena confirmation arriving twice** (retries) makes one post, not two. Task 4 test (unique key on author, kind, ref).
4. **Vietnamese text with or without diacritics, and "l33t" spellings,** must be screened the same. Task 1 test.
5. **A report about content that's since deleted** stays in the queue, readable as "content removed", and can be closed. For `child_safety`, a sealed copy of the content and the author's id is kept as evidence (`MODERATION_KEKS`, binding `["evidence", reportId]`) even if the author deletes their account. Task 7 test.
6. **Any by-id call on something the viewer can't see** (held, hidden, removed, a `club`-only author in another club, a blocked or suspended author, a deleted account) answers exactly like a missing id: same status, same body. This covers posts, comments, kudos, profiles, follows, reports and blocks. Task 4 and 5 test, parametrised over every function.
7. **A suspended person who deletes their account and signs up again** with the same email or phone stays suspended. Task 3 test.
