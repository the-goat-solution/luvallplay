# Social Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** An adults-only social layer for players (an opt-in profile, follows, a feed of matches, rank-ups, photos and short posts, kudos and comments), with the moderation that Apple 1.2 and Google's UGC policy require, built as a hidden module.

**Architecture:** A global module `social` (`scope: "global"`, `availability: "hidden"`). A player can use it when the platform availability allows it, at least one of their clubs has it on, and they've opted in (18+, community rules accepted). Rules with no I/O (text screening, who sees what, report severity, deadlines) live in `@luvallplay/core/social`. Data and queries live in `apps/web/lib/social` and in a shared `apps/web/lib/moderation` (blocks, reports, actions) that the Marketplace reuses. The API is one endpoint file per module, as lane H's split requires. The app adds a Social section under Discover.

**Tech Stack:** Next.js 16 route handlers, Postgres (raw SQL through the `Db` type, as in `lib/juniors`), `@luvallplay/api` contract, React + TanStack Router/Query in `apps/app`, `@luvallplay/crypto` (encryption plan, Task 1), `node:test`, the journeys in `apps/web/tests/e2e/journeys.mjs`.

**Spec:** `docs/plans/luvallplay-build-plan.md` §8 item 3 (Social), §4.3 (store rules), §6.8 (juniors can't use social), §7.1 (`rally-coral` only around social moments); `./2026-11-26-social-marketplace-security-index.md`.

- Hidden until gate Z passes: `availability: "hidden"` in the manifest. Every endpoint answers `404 module_off` when the player has no access. Nothing in the app shows Social without access.
- **How "hidden" still passes review (Apple 2.3.1 forbids hidden or dormant features).** `hiddenModuleOn` (`lib/juniors/switch-rule.ts:36`) gains a `social` case: on only for clubs listed in the platform setting `SOCIAL_PILOT_TENANTS` (club ids; empty by default; read in production too, unlike `JUNIORS_AVAILABILITY`). The store review demo club is the first entry; pilot clubs are added when gate Z passes. The review notes say Social is live for pilot clubs. Nothing else switches it on.
- **Access is checked in one wrapper.** `appRoute` only checks `module` for club-scoped endpoints (`lib/app-api.ts:231`), so every `social.*` handler is built with `socialRoute(id, handler)`. It runs `socialAccess` **before** body parsing and before the limiter counts, and a contract test walks every `social.*` endpoint id and expects `404 module_off` with access off.
- **Suspensions outlive accounts.** They're kept in `player_suspensions (player_id, scope 'social'|'market'|'all', until, reason_code, email_index, phone_index)`. The indexes are blind indexes of the normalised email and phone, built with `CONTACT_INDEX_KEYS` (purposes `"suspension.email"`, `"suspension.phone"`). Deleting an account never deletes these rows, and joining checks them, so re-registering with the same email or phone stays suspended.
- **People are shown by social display name and a random public id** (`social_profiles.public_id`, 12 characters, base62), never by real name or `players.id`. Avatars are **initials only** in this plan: `players.avatar_url` hasn't been through the image check (`app-account.ts:35`). A checked avatar is a later task.
- **Cross-club reads go through two `SECURITY DEFINER` functions** that the migration creates and grants to the app role. Under `TENANT_SCOPE=enforce`, `club_members` and `tenant_modules` only show the deployment's club. `social_clubs_of(player_id) RETURNS SETOF bigint` gives the clubs where the person is a member and Social is on. `shares_social_club(a, b) RETURNS boolean`. No request code uses `unscopedPool()`. Every database test file in this plan also runs under `TENANT_SCOPE=enforce` with two clubs.
- Writes use `failClosed` shared rate limits and `withPlayerLock` for daily caps (encryption plan, Task 8).
- **Adults only.** Opting in needs a confirmation that the player is 18 or over, stored with a timestamp. `players` has no date of birth, so this is a self-declaration. The store age rating is set to match (17+ on Apple, Mature or 18+ on Play), and moderators can suspend someone pending re-verification. Junior profiles have no sign-in and can never have a social profile. Community rules can't be skipped.
- Limits: display name 1–40 characters, bio ≤160, post ≤500, comment ≤300. Text is trimmed and runs of whitespace collapsed.
- Report reasons: `spam`, `harassment`, `hate`, `sexual`, `violence`, `self_harm`, `child_safety`, `scam`, `prohibited_item`, `other`. `child_safety`, `sexual`, `self_harm`, `violence` and `hate` are **serious**: they go to the platform queue, are due within **12 hours**, and email the platform moderators at `PLATFORM_MODERATOR_EMAILS` through their own sender (never the club's `ALERT_ADMIN_EMAILS`). Serious targets are shown blurred until the moderator chooses to look. Reports about a club's own owners or admins also go to the platform queue. Everything else is due within **24 hours** (Apple 1.2; inside NZ HDCA's 48 hours).
- Report details (free text, ≤1,000) are sealed with `MODERATION_KEKS`, binding `["report", reportId]`. No key, no details stored. The report itself is still accepted.
- A block works both ways: neither person sees the other's profile, posts or comments, and neither can follow the other. Blocking removes any follow between them.
- A match post names the opponent only if the opponent also has a social profile. Otherwise it reads "won a match" with the score and no name.
- Photo posts only use photos the existing check (`lib/photo-moderation.ts`) approved. `needs_review` keeps the post `held`.
- Every moderation action writes one append-only `moderation_actions` row. The app's database role can't update or delete those rows.
- Everything visible in English and Vietnamese (`packages/i18n`, new namespace `social`). UI follows the index's "Why some apps look AI-built" rules.
- Migration additive and numbered at merge. Rehearsal note in `docs/rehearsals/`.

## Review Focus

1. **Someone blocked comments on an old post** that the blocker can still see through a mutual club. The comment must not appear for the blocker, and the blocked person's comment box on the blocker's posts must refuse (`404 not_found`). Task 4 test.
2. **A player who leaves their last social club** (or the club switches the module off) keeps their data but disappears from feeds and gets `module_off`. Task 3 test.
3. **The same Arena confirmation arriving twice** (retries) makes one post, not two. Task 4 test (unique key on author, kind, ref).
4. **Vietnamese text with or without diacritics, and "l33t" spellings,** must be screened the same. Task 1 test.
5. **A report about content that's since deleted** stays in the queue, readable as "content removed", and can be closed. For `child_safety`, a sealed copy of the content and the author's id is kept as evidence (`MODERATION_KEKS`, binding `["evidence", reportId]`) even if the author deletes their account. Task 7 test.
6. **Any by-id call on something the viewer can't see** (held, hidden, removed, a `club`-only author in another club, a blocked or suspended author, a deleted account) answers exactly like a missing id: same status, same body. This covers posts, comments, kudos, profiles, follows, reports and blocks. Task 4 and 5 test, parametrised over every function.
7. **A suspended person who deletes their account and signs up again** with the same email or phone stays suspended. Task 3 test.

## Build notes

What the build really made, where it differs from the text above. Later tasks follow these.

**Task 1**
- `canSeePost` already takes `authorVisibility` (`"club" | "everyone"`) and `authorDeleted` (Task 3's security note), so Tasks 3 and 4 don't change its shape. The input type is exported as `CanSeePostInput`.
- **Decided here:** the author sees their own `held` and `hidden` posts (never a `removed` one; a deleted account sees nothing). A viewer banned in the post's club sees none of that club's posts, **even as a follower of an `everyone` author**: the ban closes the club's space, it doesn't only close the club route. A suspended author's own access is refused by `socialAccess`, not by `canSeePost`.
- `screenText` reads digits and `@`/`$` as letters **only in a word that has a letter**, so scores and prices ("21-17", "455", "$5") can't match a list word. The cost: a word written wholly in digits and symbols ("455", "@$$") isn't caught. `1` is tried as `i` (the plan's map) and also as `l`. A `@` or `$` at either end of a word is tried both as a letter and as punctuation ("@name", "word$"). Full-width letters and zero-width characters are folded away before matching. Not caught: letters spaced or dotted apart, repeated letters, other alphabets' look-alikes.
- `cleanText` saves text composed (NFC) so a letter counts once however it was typed, and answers `required` for text made only of invisible characters.
- Also exported: `POST_STATES`/`PostState`, `POST_KINDS`/`PostKind`, `SOCIAL_VISIBILITIES`/`SocialVisibility`, `TARGET_TYPES`/`TargetType`, `ReportReason`, `ReportSeverity`, `isReportReason`, `REPORT_DUE_HOURS`, `ScreenResult`.
- **The default word lists are a draft** (`word-lists.ts`: 12 `reject` entries, 28 `hold`). The owner, and a Vietnamese speaker, review the file before switch-on.
- **After review — diacritics decide for Vietnamese entries.** An entry written with diacritics matches a word typed with diacritics only when they are the same ("đủ mà", "dù mà", the name "Đỗ Ngọc" no longer match "đụ má" / "đồ ngốc"). A word typed with none still matches ("do ngoc" → the plan's own test). A `reject` entry matched only that way answers **`hold`**, not `reject`: "du ma" can't be told from "dù mà". An entry written without diacritics (English, or a list typed plain) still matches any decoration. So "screened the same" (Review Focus 4) means: caught either way; refused outright only when the text is certain.
- **Still held, for a moderator:** text typed without diacritics that spells a Vietnamese entry ("con diem nao khong" for "còn điểm…", "ca do" for "ca đó"). Left out of the defaults because they can't be made safe: "óc chó" (walnut), "cho vay" (no diacritics of its own), "đồ ngốc" (the unaccented name Do Ngoc). A word with a diacritic *and* a look-alike digit standing in for an accented vowel ("đ0 ng0c") is not caught.
- **After review — also:** "kill yourself" is in `hold` (it is said to comfort too). Plurals are their own entries ("niggers", "faggots"); there is no automatic plural. `1` is tried as `i` and `l` in every mix ("k111" → "kill"; past six 1s in a word only all-`i` and all-`l`). Marks that didn't join a letter (variation selectors, strike-through, enclosing marks) and all format characters are dropped before matching. An entry holding any symbol but a hyphen or apostrophe ("c++") is skipped whole.
- **After review — `cleanText`:** control characters are dropped (white-space ones become a space), so a NUL never reaches Postgres; direction overrides (U+202A–202E, U+2066–2069) are dropped; zero-width characters at either end are trimmed; text with nothing a reader can see (Hangul fillers, the blank braille cell, a lone mark) is `required`. Length is counted in **code points**, not graphemes: a joined emoji counts each part.

**Task 2a** (blocks, suspensions, the result type; migration `0022_social_moderation`)
- **Tables.** `social_profiles` has `public_id` and **no `suspended_until`**: suspensions live only in `player_suspensions` (one source). `social_posts` has `ref_key text` with `UNIQUE (author_id, kind, ref_key)`, `photo_id integer` → `player_photos`, and a third feed index `(author_id, created_at DESC, id DESC)`. Account and club ids are `integer` (as `players.id` and `tenants.id` are); post and comment ids are `bigint`. Lengths are checked in the database with `char_length`, which counts as `cleanText` does. A `text` post needs a body; a `match` or `rank_up` post needs its `ref_key`.
- **`player_suspensions` has no foreign key on `player_id` or `created_by`.** `tests/account-fks.test.ts` requires every foreign key to `players` to be `RESTRICT`, which would tie the account's row to the suspension; with no key the row stands whatever happens to the account. Extra columns: `action` (`suspend` | `unsuspend`: a lift is a new row), `index_kid` (which index key made the row's indexes), `created_at`, `created_by`. The reason is a code (`^[a-z][a-z0-9_]{0,39}$`), never a sentence. The index columns only take the shape of an index, so an email or phone can't be stored by mistake.
- **Who is suspended (rewritten after the 2a review; "latest row wins" is gone).** Every `suspend` row stands on its own. A person is suspended from an area when a `suspend` row for that area or `all`, with no end or an end still to come, matches them (account id, or the index of their email or **verified** phone) and hasn't been lifted. A later row never shortens or erases an earlier one; when several stand, `activeSuspension` returns the one that lasts longest. **To shorten a suspension: lift it, then write the new one.**
- **What lifts a row:** a later `unsuspend` row for the **same account id**, whose scope covers it. `all` lifts everything; `social` or `market` lifts rows of that scope only. **A lift of one area does not narrow a suspension from `all`**: lift `all`, then suspend from what stays closed. An `unsuspend` row carries no index (a database check) and never matches or lifts by email or phone.
- **`unsuspend(db, { playerId, … })` writes one lift per account whose standing suspension reaches that person**: their own (the id returned) and any earlier, deleted account whose row matches their email or verified phone. Without this a moderator could never let back in someone caught by Review Focus 7. Task 7's page just calls `unsuspend` for the person in front of it.
- **Only a verified phone counts** (`players.phone_verified_at`): when a row is written, and at lookup. `activeSuspension(db, { playerId, email, phone }, …)` uses `phone` only if it is that account's verified number (it checks); with **no** `playerId` the caller vouches for the number (pass it only when the person has just proved it). The mark is what a later call goes by, since the post is gone. `Forgotten` gained **`retainedForEvidence: number[]`** (every kept photo of the account, not only this call's); newly kept ids are logged, with no person. `deleteSocialPhotos` gained `keep?: number[]`. So after a deletion the person can also be found on those `player_photos` rows (their id, and the URLs that carry it). **Open:** nothing deletes a kept file (who and when is the owner's and counsel's: `docs/plans/store/child-safety-process.md`); its public URL still answers to anyone who has it (a private store is the fix; not built); **`deletePost` and a moderator's Remove still delete a reported post's file** (Task 4's and Task 7's files; not changed here).
- **`carrySuspensions` runs inside the transaction**, on its connection, right after the account's row is locked (`FOR UPDATE`): an email or phone changed from another device waits for the `COMMIT`. A failed deletion now rolls the carried rows back too.
- **A deadlock is tried again.** `forgetSocial` locks the account's row and then deletes follows; `block` deletes the follow and then needs the account's row (the block's foreign key). Postgres stops one of them (`40P01`). `forgetSocial` runs its whole transaction again, up to three times in all; `block` (`lib/moderation/blocks.ts`) does the same. Tested with injected errors, and once for real with a second connection doing what `block` does.
- **What is still open after the second pass:** a request let in just before the deletion that writes after it. Its rows belong to a deleted account, so nothing shows them (`socialAccess` and every gate check `deleted_at`), but they are stored. A periodic sweep of social rows whose account is deleted would close it; not built.
- **Export: a name only while the person is in sight.** `following` and `blocked` always list the public id (it is the exporter's own choice, and how to undo it); `displayName` is **null** unless the person has a live account, isn't suspended from Social, and either shares a club with Social with the exporter or has an `everyone` profile and a club with Social left (on this deployment's switch). Not the profile gate itself, which hides across a block. A deleted (merged) account is listed with a null name; it used to be left out.
- **Logs carry no message.** Both delete paths log a fixed line plus the error's name and code (`errorLabel`), never its message: a store's error can hold a photo's URL, which holds the account's id.
- **The search test reads its tables from the migrations** (every `CREATE TABLE` from `0022` on, so the Marketplace's are searched the day they exist, with nothing to add) and its columns from `information_schema`: every whole-number column is compared with the id (test accounts get ids from 700000), every text and JSON column is searched for the words and the id, sealed columns are opened and searched, and a column of a type the test doesn't know fails it. It does not keep a hand-written list to fail on; a new table is searched, not refused.
- **`TENANT_SCOPE=enforce`, confirmed:** a photo filed under another club that no post points at (uploaded and never posted, or a listing's) is invisible to this connection, so it is neither removed nor reported (`photos: 0`, `unreachablePhotoIds: []`); the test shows the rows and files still there. **Agreement pending (lane T):** a `SECURITY DEFINER` function or a platform-side sweep that removes a deleted account's photos in every club.
- **Release checks before Social runs with more than one club per deployment under `enforce`:** (1) the cross-club photo removal above exists, and a deleted two-club account leaves no `social` or `market` photo row or file anywhere; (2) kept evidence files have an owner and a retention period, or the private store is built; (3) `deletePost` and Remove keep a reported post's file; (4) the sweep of rows of deleted accounts exists or the gap is accepted in writing; (5) `lib/player-merge.ts` deletes or moves the retired account's Social rows.
- **Tests were not written first this time either:** the code changes and the new cases were written together. Nine changes were then made one at a time and undone (nothing kept; only this call's photos kept; one try; the carry on the pool; names always given; names for the suspended; the error's message logged, on either path; `block` with one try): each failed in both modes.
